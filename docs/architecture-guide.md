# Salary Predictor Technical Architecture Guide

## System Overview
The Salary-Predictor repository implements a monolithic client‑server application that predicts job salaries based on input features (e.g., job title, location, years of experience). A lightweight static HTML front‑end collects user input, which is sent to a Flask back‑end service. The back‑end loads a pre‑trained scikit‑learn RandomForestRegressor model (persisted as `models/rf_regressor.pkl`) and returns the salary estimate. Training artifacts are generated by one‑off scripts (`backend/train_model.py` and `random_forest_regression.ipynb`) that ingest the CSV dataset `data/Position_Salaries.csv` and persist model metadata (`models/metadata.json`).

## System Layers
### Presentation Layer (Frontend)
**Technologies:** HTML5, CSS, Vanilla JavaScript

Static HTML/JS assets that capture user input and render prediction results. Lives under `frontend/` and includes `index.html` and related assets (e.g., images in `assets/`). No server‑side rendering; purely client‑side interaction with the back‑end via HTTP.

### Application Layer (Backend)
**Technologies:** Python 3.x, Flask, Werkzeug

Python Flask service (`backend/app.py`) exposing REST endpoints (`/predict`). Handles request validation, model orchestration, and response formatting. Dependencies listed in `backend/requirements.txt`.

### Model Layer
**Technologies:** scikit-learn, pickle, JSON

Serialized scikit‑learn model (`models/rf_regressor.pkl`) and metadata (`models/metadata.json`). The model is a `RandomForestRegressor` trained on the CSV dataset. The layer is read‑only at inference time.

### Training Layer
**Technologies:** Python, pandas, scikit-learn, Jupyter Notebook

One‑off scripts (`backend/train_model.py`, `random_forest_regression.ipynb`) that load `data/Position_Salaries.csv`, perform preprocessing, train the RandomForest model, evaluate performance, and persist artifacts to the `models/` directory.



## Data Flow & Pipelines
1. **User Interaction** – The user opens `frontend/index.html` and fills the salary request form. 2. **HTTP Request** – The form submits a POST request (e.g., `/predict`) to the Flask application defined in `backend/app.py`. 3. **Request Handling** – `app.py` parses JSON payload, validates fields, and forwards the feature vector to the inference layer. 4. **Model Loading** – On first request (or at startup), the back‑end loads `models/rf_regressor.pkl` (a serialized `RandomForestRegressor`) and reads accompanying `models/metadata.json` for feature ordering. 5. **Prediction** – The model computes the salary estimate, which is packaged into a JSON response. 6. **Response Rendering** – The front‑end JavaScript receives the JSON, updates the DOM, and displays the predicted salary to the user.

## Key Design Decisions
- Monolithic client‑server architecture chosen for simplicity; all components reside in a single repository and run together.
- Flask selected as a minimal web framework to expose a lightweight prediction API without the overhead of larger frameworks.
- Model persisted with pickle (`rf_regressor.pkl`) to avoid re‑training on every request and to keep inference latency low.
- Static HTML front‑end keeps the UI decoupled from server logic and allows easy deployment behind any static file server or CDN.
- Training scripts kept separate from the serving code to isolate resource‑intensive operations from the low‑latency inference path.

## Scalability & Reliability
While the current implementation serves a modest workload, the following patterns enable horizontal scaling:
- **Stateless Flask Service**: The back‑end does not store session data; multiple instances can run behind a load balancer (e.g., Nginx, AWS ELB). 
- **Model Caching**: Load the serialized model once at process start and keep it in memory to avoid repeated disk I/O.
- **Containerization**: Package the back‑end (including the `models/` directory) into a Docker image for consistent deployment across environments.
- **Separate Model Server**: For high QPS, consider extracting the inference logic into a dedicated model‑serving layer (e.g., TensorFlow Serving or a FastAPI microservice) and keep Flask solely as an API gateway.
- **Static Asset CDN**: Host `frontend/` assets on a CDN to reduce latency and offload bandwidth from the Flask host.
- **Batch Prediction**: Extend the API to accept bulk requests, enabling vectorized predictions and better CPU utilization.
These steps allow the system to grow from a single‑instance prototype to a production‑grade service with minimal code changes.
